# Design

## Context

The populator is a three-phase pipeline (fetch → score → populate) with file-based handoffs (see `model-pipeline` spec). Today a run ends in `output/tier-output.json`, `tier-output.md`, and `tier-ranking.md`; getting a readable view means reading Markdown in an editor, and `populate` is the only phase that talks to LiteLLM. See proposal.md — Why for motivation.

Verified facts that shape the design:

- `fetch` and `score` never contact LiteLLM. `score` only needs provider + Artificial Analysis keys (it builds adapters and the AA client even when snapshots are cached) and reads `mappings.csv` / `models_snapshot.json` / `aa_snapshot.json` from disk when present.
- `litellm:` in `config.yaml` is consumed only as `tier_model_groups` labels by `score` and as connectivity config by `populate`. A non-LiteLLM user can leave the defaults.
- The two Markdown reports are built from different sources: `tier-output.md` from `tier-output.json` (deployments only), `tier-ranking.md` from the in-memory `ScoreResult` (ranking rows, dominators, exclusions, limit flags). `tier-output.json` does not carry the ranking-report data.
- `fetch` prints a HALT on low-confidence mappings but exits 0; `low_confidence_rows()` already exists and `score` already reads `mappings.csv`.
- The existing report is built by pure functions (`build_report(result, cfg)`, `build_markdown(payload)`) with offline tests in `tests/` (fixtures + fakes).

## Goals / Non-Goals

**Goals:**

- One double-clickable launcher on Windows that refreshes and opens a browser-readable report.
- The report is a single offline HTML file, shareable without the repo.
- The refresh path is LiteLLM-free by construction (never reaches `populate`).
- Keep the modularity rules from `model-tier-populator/AGENTS.md`: emit-layer code stays pure (data in → string out), config stays the control plane, nothing is invented.

**Non-Goals:**

- No `.exe` / PyInstaller packaging; no portable bundle; no uv/config/key bootstrapping in the launcher (user decision).
- No in-page config editing, no re-scoring from the page.
- No change to scoring/NMB/Pareto logic, the `tier-output.json` contract, or `populate` behavior.
- No non-Windows launcher (a `.sh` twin is trivial later if wanted).

## Decisions

### 1. HTML is generated natively from `ScoreResult`, not converted from Markdown

The HTML renderer becomes a third pure emit function beside `build_report`/`build_markdown`, taking the same `ScoreResult` (+ the low-confidence rows) and returning an HTML string. The `score` command writes it to `output/tier-report.html` alongside the existing three artifacts.

Why not convert `tier-ranking.md` → HTML: Markdown parsing is brittle, loses structure (cut line semantics, kind columns), and adds a dependency (or a hand-rolled parser) for no gain. Why not render from `tier-output.json` alone: the JSON lacks the ranking rows (cut models), dominators, and eligibility index, so the "why isn't X in tier Y" story would be lost.

Consequence: `tier-report.html` is always regenerated by `score`, so it can never drift from the artifacts of the same run. Opening an old HTML shows its own `generated_at`.

### 2. One self-contained file: inline CSS + inline JS, zero external references

No CDN, no web fonts, no separate assets. Sorting/filtering in the model index is ~30 lines of vanilla JS inlined in a `<script>` tag. This is what makes the file email-shareable and offline-viewable. A single-file generator keeps the emit layer dependency-free (stdlib string building + escaping; no template engine).

### 3. `refresh` is a CLI verb composing the existing phase functions, not a new phase

`cmd_refresh` calls `cmd_fetch` then `cmd_score` and stops at the first non-zero exit — the same composition `cmd_run` already does, minus `populate`. This preserves the artifact handoffs and the human-review gates (the individual commands stay available). It passes `--as-of` through to both phases like `run` does.

The batch file calls `uv run model-pipeline refresh`, then opens the browser only if that returned 0. No Python logic lives in the batch file.

### 4. Fail-loud launcher, no bootstrap (user decision)

`refresh-and-open.bat` at the populator root: `cd /d "%~dp0"`, set `SSL_CERT_FILE` if `certs\ca-bundle.pem` exists (matches the README's TLS note), run `uv run model-pipeline refresh`, `start "" output\tier-report.html` on success, and `pause` + non-zero exit on failure. Missing `uv`/config/keys surface as the raw tool error; the script does not install, copy templates, or prompt. On failure the browser is never opened — stale data is never presented as current.

### 5. Low-confidence mapping warning crosses into the report as a parameter

`score` already reads `mappings.csv`; it passes `low_confidence_rows(mappings)` into the HTML builder (and the HTML shows count + a pointer to `mappings.csv`). We deliberately do not fold it into `ScoreResult`: mappings are a fetch-phase concern, and widening `ScoreResult` would couple phases for one banner. (The Markdown ranking report gains the same banner via the same parameter so both readable outputs agree.)

### 6. LiteLLM-independence is documentation + verification, not code surgery

Verified: nothing in fetch/score dials LiteLLM. The only code-level change needed is guaranteeing `load_config` and `build_adapters` never require `LITELLM_MASTER_KEY` (they only resolve secrets on use — `LiteLLMClient` resolves it in `populate`). A regression test pins this: score completes with no LiteLLM env vars set. Docs (`README.md`, `config.example.yaml` comments) state that `litellm:` is labels-only outside `populate`.

## Risks / Trade-offs

- [HTML grows past comfort when hundreds of models are ranked] → The model index is the only large table; render every row but sort/filter client-side, and keep per-tier full rankings collapsed behind `<details>` so the page stays scannable.
- [Escaping bug could garble model names with `<`/`&`] → Emit layer HTML-escapes every interpolated value; a unit test uses hostile model names.
- [Launcher breaks if the repo moves] → It resolves paths relative to its own location (`%~dp0`), so the whole folder can be moved or copied as a unit.
- [`refresh` bypasses the low-confidence review gate like `run` does] → Accepted for click-and-run UX; the banner in the HTML (decision 5) is the compensating control. The gate remains for users of the individual `fetch`/`score` commands.
- [Two readable reports (md + html) can diverge in coverage] → Both are emitted from the same `ScoreResult` in the same `score` invocation; the model-pipeline spec delta requires coverage parity, and tests assert the HTML carries each section the Markdown report has.

## Migration Plan

Additive change; no existing artifact or command changes meaning. Old `output/` contents remain valid. Rollback = stop using the new verb/file. `README.md`/`WALKTHROUGH.md` document the new verb and file in the same change.

## Open Questions

- Whether to add a `refresh-and-open.sh` twin for non-Windows users. Deferrable; the spec scopes the launcher to Windows (.bat).
